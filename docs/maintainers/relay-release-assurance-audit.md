# Relay release-assurance codebase audit

**Date:** October 23, 2026

**Baseline:** `0f09f36a` (before this documentation update)

**Input:** Playbook Media's supplied “Website Release Assurance & Organic Growth Automation” brief

**Scope:** Local source, schemas, routes, tests, billing configuration, all 25 existing RFCs, and recorded acceptance notes. No production access, customer interviews, billing transactions, or external-site tests were performed for this audit.

## Finding

Relay has a substantial SEO and reviewed-execution foundation. The first commercial product is blocked by connections between those capabilities: production baselines and incident detection, source-backed incident repairs, checks bound to the proposed commit, production resolution verification, and a bounded paid service. More recommendation types are not the next critical dependency.

The previous roadmap combined release protection, growth campaigns, and standing approvals in its first release. It also described several implemented components as fully “Done” while their RFCs retained customer acceptance or configuration follow-ups. Preserve those historical closure decisions, but distinguish **implemented**, **live-accepted for a stated scope**, and **commercially validated** when planning the new service.

## Gaps that determine delivery order

1. **A real production baseline.** Add durable observations, known-good promotion, monitored-page coverage, confirmation, deduplication, and explicit unknown/stale states. Deployment polling must cover changes outside Relay's experiments. RFC-0019 owns this work.
2. **Repairs from incident evidence.** Current schema and service gates assume a GSC opportunity. Add a distinct, normalized regression evidence path with a verified source mapping while retaining exact-change authorization. Do not insert fake search runs or weaken the opportunity gate. New RFC-0027 owns this gap.
3. **Preview checks for the exact proposal.** Existing CI checks can be reused. Adopt customer previews first, tie the check to the actual commit, and distinguish authorization to create a branch/PR from approval to merge. Relay-owned untrusted builds are a later investment. RFC-0025 phase 1a closes the first gap.
4. **Verification of the original failure.** A merged PR, a deployment status, or a title substring is insufficient to close a general incident. Link production deployment evidence to repeated rule-specific observations. Keep attestation and unknown states separate from verified resolution. New RFC-0028 owns this contract.
5. **A service people can buy and renew.** Define readiness, agreed pages/cadence, operational failure reporting, payment evidence, cost, support effort, and renewal criteria. New RFC-0026 owns the pilot and service model; RFC-0018 consumes its records.
6. **Persistent learning after the first loop.** Reuse the existing queue filters, then extend them to page history, customer changes, proposal-time enforcement, and outcome-informed drafts in RFC-0024. Add campaigns only after repeat paid demand.

## Roadmap corrections

- Keep all existing RFC IDs and historical acceptance records. Use an explicit delivery order rather than renumbering referenced files and code comments.
- Remove the RFC-0018 ↔ RFC-0019 standing-approval dependency: monitoring and human-reviewed repairs ship first.
- Remove the RFC-0018 ↔ RFC-0025 dependency: previews do not depend on autonomy.
- Split RFC-0021's facts registry from new-page creation. RFC-0020 phase 1 needs neither; factual refreshes can depend on the registry alone.
- Let RFC-0023 check an existing customer-created launch without requiring RFC-0021. Generated pages can then consume those checks without a cycle.
- Treat basic detection and tickets as a useful pilot increment. Preserve reviewed repair as the subsequent value test.
- Separate research-credit limits from included monitoring capacity; define explicit stopped/degraded coverage instead of promising protection can never stop.
- Put configuration and live acceptance needed by each pilot on its activation checklist. Historical RFC closure does not waive a new customer's prerequisites.

## Verification and limits

The local audit ran the existing suites for `work`, `publishing`, `experiments`, `seo-checks`, `growth`, and schema parity: **70 files, 1,149 tests passed**. These tests support the capability assessment and reuse decisions. They do not validate production credentials, browser/provider availability, current GitHub installations, dual-dialect live deployments, external customer outcomes, or willingness to pay. No application code was changed by this documentation work.

Recorded live results in earlier RFCs remain historical evidence only. For example, RFC-0008's seven-day acceptance window cannot finish before October 25, and RFC-0018's multiweek check remains open. Do not convert elapsed-time or external-owner follow-ups into completed work during a local audit.
