---
title: "Track results"
description: "Confirm that an approved change reached production, then compare Search Console data before and after it."
---

Experiments & Results follows one approved pull request after Relay opens it. It shows whether the pull request merged, whether the change reached production, and what Search Console reported for the page before and after.

This is a before-and-after observation. It does not prove that your change caused a difference in traffic.

Relay never confirms a deployment on its own. When [scheduled jobs](/docs/automation) are on, a daily job refreshes each measurement and looks for deployment signals. You can also start each GitHub check and Search Console request with a click. Opening a page makes no provider request.

## Start tracking

Open an opportunity whose proposal created a pull request. In its execution history, click **Track results**. Relay pins that exact pull request, commit and page, and makes no external request. Clicking it again opens the same experiment.

Tracking needs the opportunity's original Search Console property to stay connected to the project.

## Confirm the merge

Click **Refresh GitHub status**. This only reads from GitHub. Relay checks the repository, the pull request, the approved commit and the branches. When the pull request is merged, Relay reads the changed file at the merge commit. The file must match the approved change exactly. Relay rejects a different repository, commit or file.

A merge is not proof of a deployment. Relay reuses the status for 5 minutes.

## Confirm the deployment

After the merge, click **Check signals**. Relay looks for two signals:

- **GitHub deployment:** a successful deployment of the merge commit to your production environment. Set the environment name in **Project settings → Integrations → GitHub publishing**.
- **Live page:** your page shows the approved text.

When both signals agree, click **Start measurement on the verified basis**. Relay uses the deployment time that GitHub reports. One signal alone is not enough.

If your repository does not report deployments, an administrator can enter the deployment time by hand. Describe how you confirmed it, and say whether other changes or seasonal demand can affect the page. The time must be at or after the merge, not in the future, and within the last 90 days. You cannot change it after you save it.

## Measurement windows

Dates use Google's Pacific reporting time. With the deployment date D:

- **Baseline:** the 28 days from D−28 to D−1.
- **Skipped:** D to D+6, while search engines process the change.
- **Observation:** the 28 days from D+7 to D+34.

Relay requests only final data that is at least 3 days old. The observation window ends about 38 days after the deployment.

## Refresh measurements

Click **Refresh Search Console measurements**. Each refresh makes at most one Search Console request for the page, by day. The first successful refresh saves the baseline. Later refreshes keep it and add observations. Measurement keeps working after you disconnect GitHub.

- A successful result is reused for 24 hours.
- A failed attempt can be retried after 5 minutes.
- A project can make at most 5 attempts in 24 hours, failures included.

A day that Search Console does not report shows as **Unknown**, not zero.

## Read the result

Each refresh shows one of three labels:

- **Encouraging:** clicks rose by at least 20 clicks and 20%.
- **Negative:** clicks fell by at least 20 clicks and 20%.
- **Inconclusive:** anything else.

A label other than Inconclusive also needs all 28 days in both windows, at least 100 baseline clicks, at least 1,000 impressions in each window, and no reported other changes, seasonal risk or overlapping experiment.

These are product rules, not statistical tests. Search demand, ranking updates and other site changes can move the numbers.

## GA4 supporting evidence

When the project has a Google Analytics 4 connection at the time you start tracking, each refresh also reads GA4 for the changed page. Relay counts sessions from organic search that started on that page, with the same baseline and observation dates. It uses at most 2 GA4 requests per refresh, and they do not count toward the daily limit of 5 refreshes.

GA4 never changes the label. Below it, Relay shows a statement only when the data supports it:

| Statement                      | Shown when                                                  |
| ------------------------------ | ----------------------------------------------------------- |
| Organic sessions changed by X% | Both windows have all 28 days and at least 100 sessions.    |
| Key events changed by X%       | Both windows have at least 20 key events.                   |
| Key event rate changed         | Both rules above hold.                                      |
| Revenue changed                | Both windows have revenue, and at least 20 key events each. |

Otherwise Relay shows "Too few sessions or events to compare."

- **Time zone:** GA4 reports in the property's time zone, and Search Console in Pacific time. Relay uses the same calendar dates for both and names the GA4 time zone on the page.
- **Missing days:** a day that GA4 did not report stays empty. Relay never stores it as zero.
- **Key events:** click **Key events** to choose up to 5 key events to report separately. Without a choice, Relay reports the total of all key events.
- **Failures:** when GA4 fails, or the project now uses a different GA4 property, Relay still saves the Search Console result and shows "GA4 data unavailable" with the reason.

## Long-term check

When the first result is final, click **Check again at 90 days**. Relay compares days 63 to 90 after deployment with the same baseline, using the same rules. The page shows its label as "long-term" beside the first result, which never changes. The long-term check counts toward the daily limit of 5 refreshes, and it can run once its window has started, plus the three reporting days.

## Compare and export results

The top of **Experiments & Results** counts the project's experiments by result: encouraging, inconclusive, negative, and still measuring. An experiment is still measuring until its observation window is complete. Click a count to show only those experiments. Click it again to show all.

On an experiment, click **Download CSV** to get one row for each day: the page, the date, the window, the Search Console clicks, impressions, click-through rate and position, and the GA4 numbers when there are any. Relay builds the file from saved rows and makes no Google request. A day without GA4 data has empty GA4 cells. Text that a spreadsheet would run as a formula starts with an apostrophe.

## Revert a change

When a result is negative, or you change your mind, click **Prepare revert**. Relay checks that the page still shows the approved text. Then it prepares the exact inverse change as a new proposal, which you approve like any other change. Nothing is reverted on its own.

## Permissions

Members can view experiments. Only owners and administrators can start tracking, refresh GitHub status, confirm a deployment, request measurements or prepare a revert.
